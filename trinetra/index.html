Fix and verify

For a vulnerable dependency it opens a pull request on its own branch, then re-runs the same check to prove the fix worked.

What Trinetra will not do

  • Act as an attack tool. It assesses only systems you own and authorise, from inside your own network.
  • Test outside your scope. Every target must be in a scope file signed with your key. Anything else is refused and logged, never touched.
  • Start on an unsigned scope. The signature is checked at startup. An unsigned or forged scope stops it before any check runs.
  • Reach where it shouldn't. Private, loopback and cloud-metadata addresses are blocked by default, and each connection is pinned to the address that was approved.
  • Promote a fix on its own say. Fixes arrive as pull requests. Your autonomy policy decides how far it may go, and nothing moves until the check re-runs clean.
  • Keep a record you can't check. Every action goes into a hash-chained audit log, and one command verifies the chain is intact.

What it checks today

Six detection engines, run by an agent that plans, acts, looks at what it found and plans again. Findings are deduplicated and tracked across runs, so a regression shows up as one.

Dependencies
Known vulnerabilities in the packages you ship, from the OSV database.
Committed secrets
Keys and tokens in your code, found offline and shown redacted.
Exposed files
.env files, .git folders and cloud credentials served where they shouldn't be.
Security headers
Missing or weak headers on every service in scope.
Cookie flags
Session cookies without Secure, HttpOnly or SameSite.
Surface discovery
What is actually running, added to the asset graph with its coverage.
